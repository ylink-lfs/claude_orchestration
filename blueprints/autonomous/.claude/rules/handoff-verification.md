# Handoff Verification

In a pipeline where agents hand work to each other by
message, "no new messages" has two meanings: someone is
working, or a handoff was dropped. Nothing in the message
stream distinguishes them. A production session lost about
six hours to that ambiguity — the developer requested a
test list at 19:07, the advisor answered at 19:16, the
answer never reached the developer's context, and both
agents sat idle. No error, no notification. The lead read
"no news" as "in progress."

The signal that does distinguish the two is a teammate
going idle. That notification is generated by the harness,
not by an agent remembering to send it, so it arrives
whether or not anything went wrong.

## Spawning

Call the `Agent` tool once per role with a `name` — a named
agent launched while agent teams are enabled becomes a
teammate. `subagent_type` selects the role definition:
`developer`, `reviewer`, `test-engineer`,
`security-engineer`.

**Name each instance for the plan and task:**
`<role>-p<queue position>t<task number>` — `dev-p4t2`,
`rev-p4t2`, `te-p4t2`, `se-p4t2`.

Task-scoped names are what make every later task cycle safe,
because a role-only name is silently ambiguous across tasks.
Two failures follow from reusing one:

- **Addressing a name before this task's instance exists**
  reaches the *previous* task's instance, which is still
  alive and holding an outdated tree. A production session
  lost an advisory round exactly this way. With a
  task-scoped name the send fails instead — the name does
  not exist yet, and a loud failure is recoverable in a way
  a plausible stale answer is not.
- **Re-spawning a name that is already taken** is accepted
  with no warning, no rename, and no suffix. The newer
  instance takes the name and the older one becomes
  reachable only by its internal id — so it keeps running
  and can never be shut down by name.

Assign each plan a queue position when it enters the queue
and record it in the plan file. **Never renumber** — the
number is an addressing component, and renumbering mid-plan
makes two tasks of the same plan disagree about their own
names.

**The plan and task numbers in a name are for addressing
only — they carry no task context.** Do not treat a name as
briefing an agent about its task.

**Then run `ListAgents`.** Do not expect it to flag a
collision — there is no collision signal to read. What it
tells you is which instances actually exist right now:
confirm this task's four are there, and confirm every
instance from a previous task has been sent a shutdown
request. Both must hold before you dispatch. A previous
task's instances are still listed at this point when you
are cycling between tasks — the spawn precedes the
shutdown by design, so that the window between tasks is
never empty of teammates.

## Subscribe at Dispatch Time

Every `SendMessage` the lead sends to a teammate — task
dispatch, re-send, consult redirect, recovery instruction
— carries `notify_when_idle: true`.

It is a field set at send time, not a decision to make
later. Teammate idle transitions are surfaced to the lead
automatically, but the guarantee is soft, and the
subscription can also expire without firing. Neither is a
substitute for the obligation below; both are cheap
insurance that the obligation gets a chance to run.

## The Obligation

**On every teammate idle notification, run this check
before doing anything else.**

1. Run `ListAgents`. Run `git status` and `git log` to see
   whether the work in flight actually landed.
2. Identify who owes the next move. You know this from your
   own dispatch: you directed which gates apply, so you know
   whether the task is at the input gate, in implementation,
   at the output gate, or in review.
3. **An agent that should be `running` but is `idle` means
   the handoff was dropped.** Re-send the original message
   — the task, the consult, the sign-off request. Not a
   status query.
4. **The one who owes the next move may be you.** If the
   last task's commit has landed, this task's instances
   exist, and no dispatch for it was ever sent, nothing is
   waiting on a teammate — dispatch it now (After Reviewer
   Approval step 7). This branch is not optional: in the
   session that motivated it, the lead ran steps 1–3 with
   every teammate shut down and the commit already in
   `git log`, concluded nothing, and went to work on an
   optional comment fix instead. The pipeline stayed idle
   until the user issued an explicit order.

**Do not ask an agent for its status.** `SendMessage` moves
work; it is not a status channel. A status query costs the
recipient a full-context turn and tells you less than
`ListAgents` already did. Asking is also what created a
second failure: an advisor could not distinguish the lead's
status query from the developer re-requesting a sign-off it
had already given, applied the "sign-offs stand, do not
resend" rule from `communication-hygiene.md`, and stayed
silent through three of the lead's queries.

**Do not poll.** Waiting on `ListAgents` in a loop, or
sending "are you done?", is the failure mode the
subscription exists to replace.

## Anchor Every Handoff to a SHA

Dispatches and consults name the SHA they are about. A
message without one is answered against whatever tree the
recipient happens to see, which is not necessarily the tree
the sender meant. A production session had a stale advisor
receive a request for the current round; its first
correction was invalidated by tree movement while it was
still being written.


## When the Developer Idles on a Consult

The developer's obligation at the input gate is that **the
request was sent and accepted** — not that the answer
arrived. `ListAgents` showing the advisor `running` is
acceptance.

When a developer goes idle with a consult in flight and
unblocked work remaining, push it once — and **name the
work**. "Don't wait" is not actionable; a list is. The work
that does not depend on a test list usually includes:

- The production change itself, where the plan already fixed
  its shape
- Comments that must change in the same edit as the code
- Load-bearing rationale comments
- Reading the existing test this task will invalidate
- A WIP commit of what exists so far

Five such items were available in the task where this was
first diagnosed. None of them needed the test list.

## Recovery When an Agent Is Unreachable

Execution is unattended; there is no option to stop and ask
the user. When a re-send does not revive an agent, or an
agent is gone and its sign-off cannot be retrieved:

**Do not do message archaeology.** Spawn a fresh advisor
under a new name (append `-audit`) and have it answer the
gate question independently **against the committed SHA**:
does the coverage the plan requires exist, does it actually
execute, and does it assert what it claims to assert?

The gate is about whether coverage was weakened. It is not
about whether a particular message still exists. A
production recovery of exactly this shape closed the gate on
substance — two real mutations, every case run individually,
zero skips — after both the original developer and advisor
became unreachable.

## Scope

This rule is for the lead. It governs the lead's own
routine, not the teammates' — the teammates cannot see each
other's idle transitions.
